# Feature Specification: AI Code Detection

**Feature Branch**: `001-ai-code-detection`
**Created**: 2026-02-25
**Status**: Draft
**Input**: User description: "AI Code Detection — Detect AI-generated vs human-written code per line range with confidence scores, model attribution, and multiple output formats."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Scan a Single File for AI-Generated Code (Priority: P1)

A developer suspects that a colleague's pull request contains AI-generated code. They run the scan command against the file and receive a line-by-line breakdown showing which sections are AI-generated vs. human-written, with confidence scores and model attribution for each detected region.

**Why this priority**: This is the core value proposition — the single action that answers "Is this code AI-generated?" Everything else builds on this.

**Independent Test**: Can be fully tested by scanning any source file and verifying that the output contains classified line ranges with confidence percentages. Delivers immediate value as a standalone capability.

**Acceptance Scenarios**:

1. **Given** a TypeScript file with mixed AI and human code, **When** the user runs `code-provenance scan ./file.ts`, **Then** the output displays line ranges classified as AI-generated or human-written, each with a confidence percentage (0-100%) and, where detectable, the likely AI model.
2. **Given** a file written entirely by a human, **When** the user runs the scan command, **Then** all line ranges are classified as human-written with high confidence.
3. **Given** a file generated entirely by an AI model, **When** the user runs the scan command, **Then** all line ranges are classified as AI-generated with the model identified where patterns match.
4. **Given** a file where detection signals are weak or contradictory, **When** the user runs the scan command, **Then** the system reports "unknown" for ambiguous regions rather than making a low-confidence claim, and the overall confidence level reflects this uncertainty.

---

### User Story 2 - Machine-Readable JSON Output for CI/CD Integration (Priority: P2)

A DevOps engineer integrates the scan into their CI/CD pipeline to flag pull requests containing AI-generated code above a configurable threshold. They need structured JSON output and meaningful exit codes.

**Why this priority**: Automation and CI/CD integration are what make a CLI tool stick. Without JSON output the tool is limited to manual use.

**Independent Test**: Can be tested by running the scan with `--json` flag and validating the JSON schema contains all expected fields (line ranges, classifications, confidence scores, model attributions, summary). Exit codes can be verified independently.

**Acceptance Scenarios**:

1. **Given** any scannable file, **When** the user runs `code-provenance scan ./file.ts --json`, **Then** the output is valid JSON containing line ranges, classifications, confidence scores, model attributions, and a summary.
2. **Given** a file with AI-generated code detected, **When** run with `--json`, **Then** the exit code is 1 (violations found).
3. **Given** a file with no AI-generated code detected, **When** run with `--json`, **Then** the exit code is 0 (clean).
4. **Given** an invalid or unreadable file path, **When** the user runs the scan, **Then** the exit code is 2 (error) and an error message describes the problem.

---

### User Story 3 - Identify Which AI Model Generated the Code (Priority: P2)

A security auditor needs to know not just whether code is AI-generated, but which model likely produced it — Claude, GPT, or Copilot — because different models have different known failure modes and security implications.

**Why this priority**: Model attribution is what differentiates this tool from a simple "yes/no" AI detector. It's the forensic value that makes results actionable.

**Independent Test**: Can be tested by scanning files with known provenance (code generated by specific models) and verifying correct model attribution in the output.

**Acceptance Scenarios**:

1. **Given** a code segment with patterns characteristic of a specific AI model, **When** scanned, **Then** the output attributes the segment to that model (Claude, GPT, Copilot) with a confidence score.
2. **Given** a code segment generated by AI but with no model-specific patterns, **When** scanned, **Then** the output classifies it as AI-generated with model marked as "Unknown."
3. **Given** human-written code, **When** scanned, **Then** no model attribution is assigned.

---

### User Story 4 - Scan Non-TypeScript Files with Generic Fallback (Priority: P3)

A polyglot developer wants to scan Python, Go, or Rust files. The tool provides a generic fallback parser that can analyze any text-based source file using language-agnostic heuristics (entropy, comment patterns, whitespace consistency).

**Why this priority**: The constitution mandates language-agnostic design. A generic fallback ensures the tool works on any language from day one, even if precision is lower than dedicated parsers.

**Independent Test**: Can be tested by scanning a Python or Go file and verifying that line-range classifications are produced, even though no dedicated parser exists for those languages yet.

**Acceptance Scenarios**:

1. **Given** a Python file, **When** the user runs the scan, **Then** the output contains line-range classifications using generic heuristics, with a note that a dedicated parser is not available.
2. **Given** a binary or non-text file, **When** the user runs the scan, **Then** the system returns an error indicating the file type is not supported.
3. **Given** a file with an unrecognized extension but valid text content, **When** scanned, **Then** the generic parser is used and results are produced.

---

### User Story 5 - Generate Audit-Ready Reports (Priority: P3)

A compliance officer needs a formatted markdown report documenting AI code detection results for an audit trail, including methodology metadata, evidence citations, and reproducibility information.

**Why this priority**: Forensic-grade output per the constitution. Important for enterprise adoption but not required for the core detection loop.

**Independent Test**: Can be tested by running the scan with a markdown output flag and verifying the report contains methodology metadata, evidence citations, and structured findings.

**Acceptance Scenarios**:

1. **Given** a scanned file, **When** the user requests markdown output, **Then** the report includes: scan metadata (tool version, date, algorithm versions), file summary, line-range findings with evidence citations, and overall classification.
2. **Given** the same file scanned twice with no changes, **When** comparing the two reports, **Then** the findings and scores are identical (deterministic output).

---

### Edge Cases

- What happens when the file is empty (0 lines)? System reports "No code to analyze" with exit code 0.
- What happens when the file contains only comments and no executable code? System analyzes comment patterns but reports reduced confidence due to limited signals.
- What happens when the file is extremely large (>100,000 lines)? System processes it within performance budgets (< 60s) and does not exceed memory limits (< 512MB).
- What happens when the file contains mixed languages (e.g., TypeScript with embedded SQL strings)? The primary language parser handles the main code; embedded strings are analyzed by generic heuristics.
- What happens when the file has inconsistent encoding? System detects encoding, normalizes to UTF-8 for analysis, and warns if encoding issues may affect accuracy.
- What happens when the user scans a minified file? System reports reduced confidence and flags that minification removes many detection signals.
- What happens when the file permissions deny read access? System returns exit code 2 with a clear error message.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST classify line ranges of a source file as "AI-generated," "human-written," or "unknown."
- **FR-002**: System MUST assign a calibrated confidence score (0-100%) to every classified line range.
- **FR-003**: System MUST attribute AI-generated code to a specific model (Claude, GPT, Copilot) when detectable, or "Unknown" when model-specific patterns are insufficient.
- **FR-004**: System MUST detect structural signals including: comment density and placement, variable/function naming patterns, error handling style, import organization, and function length distribution.
- **FR-005**: System MUST detect statistical signals including: lexical entropy, n-gram frequency analysis, and whitespace/formatting consistency.
- **FR-006**: System MUST provide a dedicated TypeScript/JavaScript parser that leverages language-specific syntax structures for higher-precision detection.
- **FR-007**: System MUST provide a generic fallback parser for any text-based source file using language-agnostic heuristics.
- **FR-008**: System MUST produce human-readable terminal output by default with color-coded classification indicators and clear visual hierarchy.
- **FR-009**: System MUST produce valid, structured JSON output when invoked with the `--json` flag.
- **FR-010**: System MUST produce audit-ready markdown reports when invoked with the appropriate output flag.
- **FR-011**: System MUST use meaningful exit codes: 0 (no AI code detected), 1 (AI code detected), 2 (error).
- **FR-012**: System MUST operate fully offline with zero network calls during analysis.
- **FR-013**: System MUST produce deterministic results — the same input file MUST yield identical output across runs.
- **FR-014**: System MUST include methodology metadata in all outputs (tool version, algorithm identifiers, threshold values).
- **FR-015**: System MUST report "unknown" for line ranges where detection signals are weak or contradictory, rather than guessing.
- **FR-016**: System MUST provide a file-level summary including: percentage of AI-generated lines, percentage of human-written lines, and an overall confidence level (LOW, MEDIUM, HIGH).

### Key Entities

- **ScanResult**: The complete output of analyzing a single file — contains file metadata, an ordered list of classified line ranges, and a summary.
- **LineRange**: A contiguous block of lines sharing a single classification — has start line, end line, classification (ai-generated | human-written | unknown), confidence score, model attribution (if applicable), and supporting evidence.
- **DetectionSignal**: An individual observation from a detector — has signal type, strength, location, and description. Multiple signals combine to produce a line range classification.
- **ModelSignature**: A collection of patterns characteristic of a specific AI model — used by the model attribution detector.
- **ScanReport**: A formatted representation of a ScanResult — varies by output format (terminal, JSON, markdown).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users can scan a single file and receive a complete AI vs. human classification in under 200 milliseconds.
- **SC-002**: The tool correctly classifies known AI-generated code samples with at least 80% accuracy on a curated benchmark set.
- **SC-003**: The tool produces zero false positives (classifying known human code as AI-generated) on a curated human-code benchmark set — accuracy-first per the constitution.
- **SC-004**: Model attribution correctly identifies the generating model on at least 70% of model-attributed test samples.
- **SC-005**: JSON output validates against a published schema and is parseable by standard tools (jq, JSON.parse) without errors.
- **SC-006**: The tool runs fully offline — no network calls are made during any scan operation.
- **SC-007**: Two consecutive scans of the same file produce byte-identical JSON output (deterministic).
- **SC-008**: The tool handles files up to 10,000 lines within the 200ms single-file budget.
- **SC-009**: All terminal output is readable on both light and dark terminal backgrounds.
- **SC-010**: A user unfamiliar with the tool can run their first scan and interpret the results within 60 seconds of installation.

## Assumptions

- The initial heuristic thresholds will be calibrated against a manually curated set of known AI-generated and human-written code samples. These thresholds are expected to be refined over time.
- "Confidence score calibration" in the MVP means that scores correlate directionally with accuracy — a 90% confidence claim should be more reliable than a 60% claim. Full probabilistic calibration is a post-MVP refinement.
- The TypeScript/JavaScript parser is the primary parser for MVP. All other languages use the generic fallback parser.
- Model-specific signatures (Claude, GPT, Copilot) are based on publicly observable patterns and will need ongoing updates as models evolve.
- Markdown report output is invoked via a `--format markdown` flag (or similar). The exact flag naming is a design decision for the planning phase.

## Scope Boundaries

### In Scope (MVP)
- Single-file scanning with line-range classification
- Confidence scoring (0-100%) per line range
- Model attribution (Claude, GPT, Copilot, Unknown)
- Terminal, JSON, and markdown output formats
- TypeScript/JavaScript dedicated parser
- Generic fallback parser for other languages
- Meaningful exit codes for CI/CD integration
- Fully offline operation

### Out of Scope (MVP)
- Directory or project-wide scanning (v2 — requires incremental analysis/caching)
- License violation detection
- Code theft / similarity matching against external databases
- Code lineage tracing
- IDE plugins or editor integrations
- Interactive prompts or guided mode
- Configuration files or user preferences
- Training or fine-tuning detection models on user data
